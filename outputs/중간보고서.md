# 태양광 발전 예측 + ESS 운영 시스템
## 모델보다 시스템이 중요한 이유 — 프로젝트 종합 보고서

> **한 줄 결론**: MAE 9.61의 정확한 XGBoost 예측 모델을 만들었으나, 이를 사용하는 ESS 운영 시스템(그리디 정책)이 멀티스텝 최적화를 못 해서 **완벽한 예측(Oracle)조차 단순 정책(Naive)을 이기지 못한다**는 사실을 시뮬레이션으로 발견했다. 진짜 다음 단계는 더 좋은 모델이 아니라 MPC(Model Predictive Control) 기반 시스템 설계다.

**작성일**: 2026-05-20
**프로젝트 기간**: 약 1개월
**대상**: 전국 17개 지역 시간단위 태양광 발전량 예측 + ESS 충방전 시뮬레이션

## 2. 단계별 결과 요약

### 2.1 데이터 진단 (Phase 1)

| 발견 | 영향 받는 지역 | 진단 |
|---|---|---|
| 분포 shift (2022→2023) | 전남 | KS-statistic 0.099, p-value 0.0 → 명확한 분포 차이 |
| 피크 시간대 데이터 결측 | 충남 | 10~14시 데이터 완전 결측 — 수집/전처리 오류 |
| 이상치 과다 | 전남 | IQR 이상치 4.1% (전국 평균 2.0%의 2.1배) |
| 설비 급증 | 충남 | 2019년 +203% 급증 → 학습 분포 왜곡 |

**의미**: 두 지역(전남·충남)이 전체 가중치의 약 41.5%를 차지하면서 **모든 모델의 공통 약점**이 됨. 이는 이후 모든 실험에서 일관되게 확인됨.

### 2.3 검증 실험 1 — 전남 분리 학습 (폐기됨)

전남이 가장 큰 약점이라 단독 모델로 분리하면 나아질 거라는 가설.

| 지표 | 통합 모델 | 분리 학습 | 변화 |
|---|---|---|---|
| Simple Avg MAE | 9.59 | 10.66 | **+11.2% 악화** |
| Weighted MAE | 31.91 | 34.44 | +7.9% 악화 |
| 전남 ESS 점수 | 24.60 | 24.50 | -0.4% (≒0) |
| 가중평균 ESS 점수 | 28.67 | 28.63 | -0.1% (≒0) |
| **충남 MAE** | 11.25 | **17.22 (+53%)** | **하지만 ESS 점수는 0% 변화** |

**폐기 결정** — 이 실험에서 **첫 번째 핵심 발견** 등장.

### 2.4 검증 실험 2 — AutoGluon v1/v2 (XGBoost가 우월)

| 지표 | XGBoost | AutoGluon v1 | AutoGluon v2 |
|---|---|---|---|
| Simple Avg MAE | **9.61** | 18.21 | 18.10 |
| Weighted MAE | **31.91** | 57.53 | 56.89 |
| 전남 MAE | **90.04** | 143.45 | 141.56 |

**AutoGluon은 모든 지표에서 XGBoost 대비 약 2배 큰 오차**. v2에서 트랜스포머(TFT, PatchTST) 4개를 추가 학습했으나 **앙상블 가중치 0%**로 모두 제외됨.

### 2.5 ESS 시뮬레이션 — 핵심 발견의 무대

ESS 시뮬레이터를 만들고 4가지 정책을 비교:

| 정책 | 가중평균 자급률 | ESS 점수 |
|---|---|---|
| **naive_baseline** | **75.90%** | **44.23** |
| xgb_no_lookahead | 75.90% | 44.23 |
| xgb_lookahead | 74.47% | 42.32 |
| **oracle** (완벽한 예측) | **74.24%** | **41.94** |

**결과 해석**:
- 단순한 Naive가 1위
- XGBoost lookahead는 더 나쁨
- **Oracle(완벽한 예측)조차 Naive에게 짐**

여기서 **두 번째와 세 번째 핵심 발견** 등장.

## 3. 핵심 발견 3가지

### 🔑 발견 1: MAE ≠ ESS 점수

전남 분리 학습 실험에서 결정적으로 드러남:

```
충남:
  분리 학습으로 MAE +53% 악화 (11.25 → 17.22)
  ESS 점수 변화: 0.00 (25.94 → 25.94)
```

**MAE는 절댓값 정확도, ESS 점수는 충방전 결정의 방향성**이다. 두 지표는 다른 차원이다. 모델 성능 개선이 항상 운영 성능 개선으로 이어지지 않는다.

**의미**:
- "MAE만 보고 모델 선택하면 잘못된 결정을 내릴 수 있다"는 실증
- 의사결정 시스템에 쓰일 예측 모델은 **태스크 직결 지표(ESS 점수)로 평가**해야 한다는 교훈

### 🔑 발견 2: 좋은 예측 + 그리디 시스템 = 가치 못 만듦

ESS 시뮬레이션에서 가장 강력한 발견:

```
Naive 75.90% > XGBoost(MAE 9.61) 74.47% > Oracle(완벽한 예측) 74.24%
```

**완벽한 예측을 가져와도 그리디 정책 안에서는 단순한 Naive보다 손해**다. 왜?

**메커니즘**:
- 그리디 정책의 lookahead는 "다음에 더 큰 잉여가 오니까 지금 비워두자"고 결정
- 하지만 **지금 받지 않은 잉여는 영원히 손실** (저장 안 한 발전은 그냥 버려짐)
- 미래에 또 잉여가 와도, 과거의 잉여를 되살릴 수는 없음

Oracle이 같은 lookahead 정책을 쓰니까:
> "미래를 완벽히 알지만, 그 정보로 할 수 있는 거라곤 SOC 범위 좁히기뿐"

**의미**: 예측의 가치는 의사결정 시스템의 능력에 의해 제한된다. 시스템이 멀티스텝 최적화를 못 하면 예측이 아무리 좋아도 무용지물.

### 🔑 발견 3: 진짜 다음 단계는 모델이 아니라 시스템 (MPC)

위 두 발견의 자연스러운 귀결.

**진짜 예측의 가치를 발휘하려면**:
- 미래 N시간을 한 번에 보고
- 그 N시간 전체의 손익을 합쳐서
- 지금 일부러 손해 보는 결정도 할 수 있어야 함

**비유**:
> "내일 아침 시리얼이 떨어진다는 걸 알았어.
> 그래서 어젯밤 마트 갈 때 시리얼을 평소보다 2배 사뒀어.
> 어제는 짐이 무거워서 손해 봤지만, 오늘 아침은 안 굶었지."

"지금 손해 보고, 나중 더 큰 손실을 막는다" — 이게 진짜 예측의 가치다. 이를 가능하게 하는 게 **MPC (Model Predictive Control)**.

**현재 그리디 시뮬레이터의 한계**:
- 매 시점 그 시점만 보고 최적화 (1-step)
- 미래 정보가 있어도 활용 못 함
- 결과: Oracle도 못 이김

**MPC의 작동 방식**:
- 매 시점 N시간 lookahead로 SOC 시퀀스 전체 최적화
- "지금 채우지 않으면 4시간 뒤 더 큰 잉여를 버려야 함"을 미리 계산
- 결과: 정확한 예측이 진짜 가치를 만듦

## 4. 그래서 어떻게 할 것인가

### 4.1 단기 (1~2주) — API 제공 (퍼실 조언)

XGBoost 모델을 FastAPI로 감싸서 REST API 제공:

```
POST /predict
  input: {region, timestamp, weather_forecast}
  output: {predicted_power_mwh, confidence_interval}

POST /predict_24h
  input: {region, start_time, weather_forecast_24h}
  output: {predictions: [...], total_mwh: ...}
```

**범위 명시**: 이 API는 **예측값만 제공**한다. 이를 사용하는 의사결정 시스템(MPC)은 별도 설계가 필요하다는 점을 문서화.

본격 구현 전 **개념증명** 수준으로:
- 단일 지역 (전남 또는 충남, 가중치 큰 지역)
- 24시간 lookahead
- `scipy.optimize` 또는 `cvxpy`로 SOC 시퀀스 최적화
- **비교**: 그리디 vs MPC, 각각의 자급률·ESS 점수

**기대 결과**: MPC가 그리디를 명확히 이김으로써 발견 3을 실증.

### 4.3 장기 — 본격 시스템 (본 프로젝트 범위 밖)

- 17개 지역 전체에 MPC 적용

## 6. 메타 통찰 — 이 프로젝트의 진짜 가치

### 6.1 "잘못된 가설을 발견한 가설"

처음엔 "더 좋은 모델 = 더 좋은 운영"이라는 암묵적 가정으로 시작했다. 이 가정이:
1. **전남 분리 학습**: MAE 악화에도 ESS 점수 무변화로 처음 흔들림 (발견 1)
2. **Oracle 시뮬**: 완벽한 예측이 Naive에 짐으로써 결정적으로 깨짐 (발견 2)

**가정이 틀렸다는 사실 자체가 발견**이며, 이는 단순히 "좋은 모델을 만든 것"보다 가치 있는 결과다.

### 6.2 "시스템 사고"의 중요성

모델 평가 지표(MAE) → 운영 지표(ESS 점수) → 비즈니스 지표(자급률)의 **연결 고리**를 명시적으로 측정했기 때문에 격차를 발견할 수 있었다.

**일반적인 ML 프로젝트가 빠지기 쉬운 함정**:
- MAE만 보고 모델 선택 → 운영에서 가치 못 만듦을 모름
- 모델만 개선하고 시스템은 그대로 둠 → ROI 낮은 투자 반복

본 프로젝트는 이 함정을 **시뮬레이터를 통해 명시적으로 드러냄**.

### 6.3 다음 ML 프로젝트에 적용할 수 있는 교훈

1. **태스크 직결 지표로 평가하라** — 예측 MAE가 아니라 사용처의 성과 지표
2. **시스템 전체를 한 번에 사고하라** — 모델은 그 일부일 뿐
3. **완벽한 예측의 가치를 측정하라** — Oracle 시뮬은 "예측 개선의 천장"을 알려준다
4. **AutoML은 보조 도구다** — 도메인 지식 기반 튜닝을 대체하지 못한다

## 부록 A. 환경 트러블슈팅 (재현용)

### A.1 AutoGluon v1: Chronos 계열 4개 학습 실패

```
ImportError: cannot import name 'size_hint' from
  'torch.fx.experimental.symbolic_shapes'
```
- 원인: Colab Enterprise 기본 torch 2.10.0과 chronos/transformers ABI 불일치
- 영향 모델: Chronos2, Chronos2SmallFineTuned, ChronosWithRegressor, DeepAR

### A.2 AutoGluon v2: TFT/PatchTST 학습 실패

```
AttributeError: partially initialized module 'torchvision'
  has no attribute 'extension'
```
- 원인: torchvision 0.25.0+cu128과 다운그레이드된 torch 2.9.1의 빌드 ABI 불일치
- 해결: 런타임 완전 재생성 → `torchvision==0.24.1`, `torchaudio==2.9.1` 명시 설치

### A.3 핵심 교훈

- AutoGluon의 deep learning 모델은 PyTorch 생태계 버전 일관성에 매우 민감
- Colab Enterprise 기본 환경 ≠ AutoGluon 요구사항 → 항상 충돌 위험
- **학습 시작 전 환경 검증 셀(import 체인 테스트) 사전 분리** 필요
